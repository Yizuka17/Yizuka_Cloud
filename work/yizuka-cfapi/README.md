# Yizuka Cloud Files API test client

This Windows Cloud Files API client is installed alongside the existing rclone/WinFsp `Z:` drive. It uses a separate sync root and the remote `CFAPI端到端测试` directory. It does not replace `Z:` or project the production cloud root.

The test installer is `outputs/小云盘/YizukaCloudFilesSetup-Test.exe`. It asks for a local NTFS/ReFS cloud-folder path, username, and password. The folder is the on-demand cache location. The installer verifies the account, trusts the development signing certificate for the current Windows user, installs the MSIX package, and starts the client. It reuses the existing encrypted authorization if the password field is left blank. The test root appears in Explorer as `Yizuka Cloud (test)`.

The packaged client selects loopback, LAN, or Cloudflare automatically. It uses Cloud Files API placeholders and range downloads, Copyparty up2k chunked uploads for large files/public routes, and a Windows Shell thumbnail provider that requests server-generated JPEGs. On the first thumbnail request in a folder, the provider prefetches missing media thumbnails with at most four concurrent requests and stores them in a persistent local cache keyed by path, size, and modification time. Subsequent folder visits read cached JPEGs without downloading full files; prefetch does not run until Explorer asks for a thumbnail. The client also provides a tray menu for opening the web page/folder and triggering refresh, and an hourly metadata refresh. The sync root permits Windows to dehydrate clean placeholders when it needs space. File/folder create, edit, rename, and delete operations have isolated end-to-end tests. Observed file deletes and folder moves/deletes are journaled before syncing; on restart, changed remote versions are preserved rather than deleted. Synced file metadata is snapshotted so local edits made while the client is stopped can be uploaded after restart; simultaneous changes are withheld to preserve both sides. The thumbnail COM server exits after two idle minutes. The website cloud mark, setup EXE, MSIX app, tray, and Explorer sync root use the same blue cloud artwork.

Test with `C:\Program Files\dotnet\dotnet.exe run -c Release --project work\yizuka-cfapi\yizuka-cfapi.csproj -- cfapi-test-no-shell`. This creates only isolated temporary sync roots and uses the test remote folder. `route-test`, `thumbnail-route-test`, `up2k-test-small`, and `up2k-test-public` exercise network paths. `refresh-now` tells the installed client to sync immediately.

This is still a test release. Explorer F5 itself does not yet call the refresh command. Local deletions made while the client is completely stopped are not inferred as cloud deletions on restart. Cloud conflicts are detected using WebDAV size and second-resolution modification time because this Copyparty endpoint does not emit ETags; rapid same-size edits within one second could be missed. The current root has no cache-size limit or automatic dehydration. Login-start behavior is declared in the MSIX manifest but has not been verified by logging out or rebooting this computer. Do not use the test installer as the sole copy of important files.
